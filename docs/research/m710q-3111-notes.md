# ThinkCentre M710q (board 3111): running recon notes

The counterpart to `ec-decode-m70t.md`, for the second board. Findings get
added here as they arrive, newest section last. Each entry says how it was
established, because that is what separates a fact from a guess later.

Nothing here has been established by code yet. The app has never run on this
board.

## Observation 1 — a fan RPM is already readable by at least one tool

**Source:** reported by the operator from their own machine, 2026-09-13. Not
reproduced by anything in this repo.

| Tool | What it shows |
|---|---|
| LibreHardwareMonitor | No fans at all |
| HWMonitor | 1 fan with an RPM, 2 fans with no reading |

### Why this matters

On the reference M70t Gen 6, **no** tool could read the fan. That is the
premise of the whole project: the ACPI embedded controller is stubbed, so
every tool that asks it politely gets `0`, and the real tachometer is only
reachable by talking to the physical EC directly.

A tool printing a real RPM on the M710q means a working path already exists
there. If that path is one an existing program can already drive, this board
may need none of the EC reverse-engineering the M70t required.

### Leading hypothesis: a Super I/O monitoring chip

Three tachometer inputs with one populated is the characteristic shape of a
Super I/O hardware-monitoring chip on a board with three fan headers and one
fan fitted. An M710q Tiny has one fan, which fits.

The M70t had **no Super I/O** — `recon/lhm-enum.txt` shows LibreHardwareMonitor
finding only the motherboard and the CPU, no monitoring chip, no fans. The
design spec records that absence as the reason control had to go through the
EC at all. A board that *does* have one is in a materially better position:
FanControl already drives supported Super I/O chips including their PWM duty,
which would be the real 0-100% control the M70t could never reach.

### Two things this observation does NOT establish

1. **That LibreHardwareMonitor found nothing.** Without Administrator rights
   LHM cannot load its kernel driver, and then shows no monitoring chip and no
   fans — which is exactly the reported symptom. Until LHM has been run
   elevated, its silence is not evidence.
2. **That the M710q differs from the M70t here.** The M70t was tested against
   Task Manager, HWiNFO, LibreHardwareMonitor and Vantage. CPUID's HWMonitor
   is not on that list. So either this board exposes a fan the M70t does not,
   or CPUID HWMonitor reads both and the "every tool reports 0" claim was
   never tested against it. The second case would be a finding about the
   reference board too, and would be worth reporting upstream.

## Observation 2 — there is no Super I/O. The hypothesis above is dead.

**Source:** reported by the operator, 2026-09-13, answering the three checks
in observation 1.

1. The tool showing the fan is **CPUID HWMonitor**, not HWiNFO.
2. The node above the fan readings is the **motherboard name**, not a chip
   name.
3. LibreHardwareMonitor **run as Administrator still shows no fans**.

### What each answer rules out

**No Super I/O.** LibreHardwareMonitor's Super I/O coverage is broad — ITE
IT87xx, Nuvoton NCT6xxx, Fintek, Winbond. Elevated, with its driver loaded,
it finds no monitoring chip and no fans. That absence is now evidence rather
than a missing permission, and it matches the M70t exactly.

**FanControl will not help.** FanControl reads sensors through
LibreHardwareMonitor's stack. If LHM sees no fans, FanControl sees no fans.
The zero-code shortcut is closed. This board needs the same kind of work the
M70t needed.

**HWMonitor reads the fan from somewhere that is not a Super I/O.** It shows
the value under the motherboard node, which is where CPUID's tools put
readings taken from an embedded controller or from ACPI rather than from a
monitoring chip. Which of those two it is remains unknown, and only matters
as a hint — what matters is that a real tachometer value exists and is
reachable.

**The M70t comparison is still open.** The reference board was tested against
Task Manager, HWiNFO, LibreHardwareMonitor and Vantage. CPUID HWMonitor is
not on that list, so it is still not established whether the M710q exposes
something the M70t does not, or whether HWMonitor would have read the M70t
too. Worth reporting upstream either way.

### Consequence: back to the EC route, with one real advantage

The plan reverts to `scripts/recon/`, and `03-dump-ec.ps1` is the deciding
experiment — exactly the question the M70t's own recon turned on. The prior
is good: something already reads a real RPM on this board without a Super
I/O, and the embedded controller is the most likely source.

The advantage the reference project never had is the RPM value itself. On
the M70t nothing could read the fan, so the tach offset had to be found the
long way: dump EC RAM at idle, dump it under load, diff the two, and
correlate what moved. Here, HWMonitor states the number. Read it at the
moment of the dump and search EC RAM for that exact value, and the offset
falls out of a single dump.

`03-dump-ec.ps1` now takes `-KnownRpm <value>` for this, and reports any EC
word holding that value, closest first. Confirming it still needs two dumps —
the same offset must hold the idle value and the loaded value — but finding
the candidate no longer does.

`02-probe-wmi.ps1` also now enumerates ACPI fan devices (`PNP0C0B`). Windows
enumerated five on the M70t and they all reported nothing, because they
routed through its stubbed EC. If this board enumerates them and something
can read a real RPM, `_FST` and `_FIF` are worth a look in the decompiled
tables from script 1.

### Still deliberately not built

A Super I/O detection probe. Identifying one means entering configuration
mode on ports 0x2E/0x4E, a riskier operation than anything the current recon
scripts do — and observation 2 has now answered the question anyway.
